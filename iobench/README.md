# File read benchmark

`iobench` uses conventional libc descriptor I/O and the startup clock grant.
The normal build installs `iobench.pxe` and `share/iobench.bin`, a deterministic
1 MiB fixture generated by host Lua. Byte at zero-based offset `i` is
`(i ^ (i >> 8) ^ (i >> 16) ^ 0xa5) & 255`.

```text
iobench read app://share/iobench.bin
iobench read app://share/iobench.bin --buffer 64 --rounds 5
```

The URI must contain exactly this fixture; arbitrary files are rejected.
`--buffer` is a positive decimal application request size, 1..65536 (default
4088). `--rounds` is 1..100 (default 5). There is always one untimed, verified
warm-up pass. Every pass opens a fresh read-only descriptor and closes it after
verification. No input file is created or modified.

Prepare a disposable RAM copy manually, outside the benchmark. Shell output
redirection truncates an existing destination, so first choose a new name:

```text
cat app://share/iobench.bin > home://iobench.bin
iobench read home://iobench.bin
rm home://iobench.bin
```

For `host://`, place the installed `share/iobench.bin` in a dedicated host export
before boot, then run `iobench read host://iobench.bin`. The export may be
read-only. Compare request sizes 64, 512, 4088, 4096 and 65536 with the same
fixture, placement and environment. Run only one selected workload at a time.

## Timing and interpretation

The program allocates a 1 MiB result buffer once, and clears it before each pass.
The request size controls individual `read()` calls into successive positions
of this retained buffer; it is not the allocation size. The last request is
clamped to the remaining fixture bytes. A pass times only the payload read loop,
including call/byte accounting. Opening, buffer preparation, the additional EOF
probe, byte-for-byte verification, closing and report output are outside timing.
There is no logging inside that loop. Reports go to stderr; stdout is unused.

`requested` is the fixed payload goal, not the sum of request capacities across
short reads. `completed` counts bytes actually returned. `read_calls` counts
payload read attempts (including a failed read or premature EOF); `short_reads`
counts positive results below that call's request. The separate EOF probe is
not counted. `failed_pass` is 0 or 1, including setup, clock, read, verification
and close failures; diagnostic lines identify the cause. A failure stops the
remaining passes, returns nonzero and suppresses that pass's throughput and the
successful-run summary. Already completed samples remain visible.

Current native FILE reads return at most 4088 bytes. Libc `read()` performs one
transfer, so 4096 and 65536 requests normally produce positive short reads;
the benchmark loops over the remainder. Both need 257 payload calls for 1 MiB,
as does the 4088 request size. These are application calls, not an instrumented
syscall count. Other transports may have additional internal calls.

The existing monotonic clock measures elapsed time, not CPU time. A separate
1000-call loop reports mean clock-call plus loop overhead, without subtraction.
The two timing boundaries still contribute overhead and nanosecond units do not
imply nanosecond accuracy. Each successful sample prints elapsed nanoseconds and
MiB/s. The summary reports median elapsed time, minimum/maximum, and throughput
computed from the median elapsed time. For even sample counts the middle two
elapsed values are averaged. This is neither a tail-latency distribution nor a
statistical confidence estimate.

The warm-up and verification affect cache state. Reopening a descriptor does
not make backend or host caches cold. Record CPU count/placement, guest RAM,
accelerator, host CPU/OS/virtualization, other guest tasks, repository revisions
and any virtio-fs setup with results. Keep nested-VM and owner's host results
separate. Pyxis owns the integrated manual commands and initial observations in
its I/O and IPC milestone documentation.
